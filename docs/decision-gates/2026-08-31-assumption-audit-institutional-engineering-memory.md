# Assumption Audit — Institutional Engineering Memory / Capability OS

Date: 2026-08-31
Status: OPEN — NOT A PRODUCT DECISION
Purpose: attempt to falsify the hypothesis that an internal system linking projects, repositories, capabilities, assets, research, dependencies, evidence, and decisions creates enough institutional value to justify building and maintaining it.

## Hypothesis

> An internal, evidence-aware institutional graph can materially reduce duplicated work, improve reuse/discovery, preserve engineering memory, and improve portfolio/project decisions across a large multi-project organization.

This is an internal-utility hypothesis. External commercialization is explicitly out of scope until separately proven.

## What the market already provides

### Backstage
Backstage already provides a software catalog for services, websites, libraries, data pipelines, ML models, APIs, resources, ownership, systems, domains, and relationships such as `dependsOn`, `partOf`, `ownedBy`, `providesApi`, and `consumesApi`. Backstage explicitly supports custom entity kinds/types and can manage thousands of components.

Implication: generic software catalog / dependency / ownership discovery is NOT a novel requirement.

### Portfolio-management platforms
Enterprise portfolio tools already cover strategy, projects, investment, resources, dependencies, and outcome-oriented portfolio management. Generic portfolio visibility is therefore NOT a sufficient reason to build.

### Repository / code intelligence
Open-source and commercial repository-intelligence systems already provide code graphs, dependency analysis, semantic search, impact analysis, and RAG-style code understanding. Generic "LLM + graph over repos" is NOT a sufficient differentiation.

## Adversarial assumptions

| ID | Assumption | Current status | What would falsify it? |
|---|---|---|---|
| A-01 | Our organization has enough project volume/complexity that a unified internal model creates material value. | OPEN | A representative sample shows low duplication, low cross-project reuse, or little navigation/search cost. |
| A-02 | Existing tools cannot be composed cheaply enough for our internal needs. | UNPROVEN | Backstage + GitHub + project management + docs + CI + search provide adequate coverage with modest integration effort. |
| A-03 | The missing layer is semantic cross-project capability/asset lineage rather than ordinary catalog metadata. | OPEN | Human review shows most needed relations are already represented by existing catalogs/dependency systems. |
| A-04 | AI-assisted relationship discovery materially improves human-only discovery. | UNPROVEN | Blind evaluation shows no meaningful precision/recall/time advantage. |
| A-05 | Relationship accuracy can be maintained without creating more operational burden than value. | OPEN | False-positive/false-negative rates or metadata maintenance cost become dominant. |
| A-06 | Reusable capabilities can be identified at a useful granularity. | OPEN | Humans disagree heavily or discovered "capabilities" are too vague/unstable to reuse. |
| A-07 | The system can remain evidence-grounded rather than becoming a speculative graph generated by an LLM. | OPEN | A substantial fraction of high-value relations cannot be supported by repository/docs/runtime evidence. |
| A-08 | Shared institutional capabilities reduce duplication enough to justify maintenance. | OPEN | Measured avoided work is below build+maintenance cost. |
| A-09 | Project decisions improve when the institutional graph is available. | UNPROVEN | Blinded or controlled decision tests show no improvement in prioritization/merge/archive/reuse decisions. |
| A-10 | An internal system is preferable to buying an existing platform. | UNPROVEN | A composed/off-the-shelf stack provides equal value at lower TCO and acceptable lock-in. |
| A-11 | The system can eventually support opportunity discovery/composition without becoming an unbounded platform. | SPECULATIVE | Useful outputs require broad uncontrolled scope or cannot be evaluated with bounded experiments. |
| A-12 | Building for ourselves does not create a maintenance trap. | OPEN | 12-month ownership cost, integration churn, security burden, or dependency upgrades dominate expected value. |

## Required Kill Tests

### Kill Test 1 — Existing-stack composition

Attempt to achieve the desired internal workflow using existing components before writing custom graph infrastructure:

`Backstage + GitHub + project tracker + documentation/search + CI + existing knowledge/graph tooling`.

Measure setup effort, missing capabilities, data freshness, query usefulness, and maintenance burden.

### Kill Test 2 — Real portfolio sample

Take a representative sample of our own repositories/projects. Measure:

- duplicate or near-duplicate implementations;
- shared capabilities;
- cross-project dependencies;
- undocumented ownership;
- research-to-project reuse;
- abandoned/obsolete assets;
- time required for a human to answer these questions.

No build decision before this baseline exists.

### Kill Test 3 — Blind relationship discovery

Compare:

A. human-only analysis;
B. deterministic/static analysis;
C. AI-assisted analysis.

Measure precision, recall, review time, and false-positive cost for relationships such as `duplicate`, `depends_on`, `implements_capability`, `reuses`, `supersedes`, and `candidate_merge`.

### Kill Test 4 — Capability extraction utility

Ask whether extracted capabilities lead to an actual reuse or consolidation decision. A graph full of nouns is not evidence of utility.

### Kill Test 5 — Decision improvement

For real project triage cases, hide the graph from one condition and expose it in another. Compare decision quality, consistency, time-to-decision, and missed reuse opportunities.

### Kill Test 6 — Build-vs-compose TCO

Calculate total cost of ownership for:

- internal custom system;
- composed OSS stack;
- commercial platform;
- hybrid approach.

Include integration, maintenance, security, upgrades, migration risk, and opportunity cost.

## Current market evidence

Backstage's official documentation states that its catalog tracks components, APIs, resources, ownership, systems, domains, and well-known relations including dependencies and composition. It also explicitly says the catalog can be extended with custom types and that catalog data should not necessarily be treated as the ultimate source of truth.

## Current decision

The generic hypothesis "build an internal portfolio/project graph" is NOT validated and must not be treated as a product direction.

The only remaining hypothesis worth testing is narrower:

> Can an evidence-grounded, capability-centric internal model reveal materially useful relationships across our own large repository/project portfolio that existing tools and a reasonable composed stack fail to reveal or maintain economically?

If Kill Tests 1–6 fail, stop.

## Anti-bias rule

A useful internal artifact is not automatically a startup opportunity. External commercialization requires a separate five-pillar venture test with independent buyer/WTP evidence.
